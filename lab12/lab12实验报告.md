## 2. 实验原理

### 2.1 系统结构

系统由一个 RV32I 五段流水线 CPU 和一组内存映射外设组成。CPU 的指令接口接 64KB 指令存储器，数据接口接总线译码模块。总线译码根据数据地址的高位把访问分派给数据存储器、字符显存、键盘、定时器、开关和 LED 等设备，再把选中设备的数据送回 CPU。

CPU 的时序约定与实验十相同：时钟上升沿读指令、读数据存储器、写寄存器堆，下降沿更新 PC 和四个段寄存器，并写入数据存储器。外设寄存器统一在时钟下降沿写入，读通路是组合逻辑，由 MEM 级的地址直接译码。这样外设的写时刻与数据存储器一致，读数据在下一个下降沿被 WB 级采样。

系统时钟由板上 100MHz 晶振四分频得到。CPU 时钟取 10ns 高电平的脉冲，像素时钟取 50% 占空比的方波，两者同源，周期都是 40ns。显存用异步读的分布式 RAM，CPU 写端口和 VGA 读端口分开，不需要处理跨时钟域。

### 2.2 内存映射

数据地址 32 位，按高位划分设备，具体分配见下表。

| 地址 | 大小 | 设备 | 访问方式 |
| :--- | ---: | :--- | :--- |
| `0x0000_0000` | 64 KiB | 指令存储器，16K 字 | 取指，只读 |
| `0x0010_0000` | 128 KiB | 数据存储器，32K 字 | 按 `memop` 读写字节、半字、整字 |
| `0x0020_0000` | 4 KiB | 字符显存，32 行 × 128 列 | 按字节写，可读回 |
| `0x0021_0000` | 4 B | 显示起始行 `top_row` | 写 |
| `0x0021_0004` | 4 B | 光标 `{物理行[4:0], 列[6:0]}` | 写 |
| `0x0030_0000` | 4 B | 键盘数据，低 8 位 ASCII | 读，不出队 |
| `0x0030_0004` | 4 B | 键盘状态，bit0 有数据，bit1 溢出 | 读 |
| `0x0030_0008` | 4 B | 键盘弹出 | 写任意值 |
| `0x0040_0000` | 4 B | 毫秒定时器 | 读 |
| `0x0050_0000` | 4 B | 拨动开关 `SW[15:0]` | 读 |
| `0x0060_0000` | 4 B | `LED[14:0]` | 写 |
| `0x0060_0004` | 4 B | 数码管调试值 | 写 |

指令存储器用 `addr[15:2]` 做索引，覆盖 64KB。数据存储器用 `addr[16:2]` 做索引，覆盖 128KB，数据段的起点 `0x0010_0000` 正好落在 0 号单元，栈顶 `0x0011_FFFC` 落在最后一个单元。如果误用 `addr[15:2]`，`0x0010_0000` 和 `0x0011_0000` 会别名到同一片 64KB，数据段和栈互相覆盖。

`0x0020_0000` 和 `0x0021_0000` 的高 12 位都是 `0x002`，只比较高 12 位无法区分显存和控制寄存器。本设计用 `addr[31:16]` 选中显存，用整字地址精确比较选中控制寄存器，避免别名。

写使能按设备分别产生：

```verilog
wire sel_dmem = (addr[31:20] == 12'h001);
wire sel_char = (addr[31:16] == 16'h0020);
```

数据存储器和字符显存只在对应段内才接受写，其它设备各自用整字地址比较。

### 2.3 外设的读写类型

按照外设由谁更新，映射寄存器分成三类：

| 类型 | 例子 | 实现 |
| :--- | :--- | :--- |
| CPU 只读 | 定时器、开关、键盘状态 | 输出端口直接接组合逻辑，读时选通 |
| CPU 只写 | 起始行、光标、LED、数码管 | 下降沿锁存，CPU 不读 |
| 外设写入 | 键盘数据 FIFO | 键盘硬件写，CPU 只读和弹出 |

键盘数据寄存器不能让读操作产生副作用。CPU 没有独立的 load 使能信号，`dmemaddr` 在一次访存中会保持多个时钟周期，如果读数据寄存器就弹出队首，一次按键会被消费多次。本设计把读数据和出队分开：读 `0x0030_0000` 只取出队首，写 `0x0030_0008` 才把读指针前移。

### 2.4 字符显存与 VGA 显示

VGA 采用 640×480、60Hz 时序，像素时钟 25MHz。屏幕划分为 30 行、70 列的字符阵列，每个字符占 16 行、9 列像素：

$$30\times 16 = 480,\qquad 70\times 9 = 630.$$

字符显存定义 32 行 × 128 列，多出的两行做环形缓冲。显示时用

$$\mathrm{disp\_phys} = (\mathrm{top\_row} + v\_row) \bmod 32$$

把屏幕上的行号换算成显存中的物理行。软件滚屏时只需把 `top_row` 加一，再清空新的最底行，不必搬动整屏内容。

每个字符格在显存中只保存 8bit ASCII 码。显示一行字符时，先用 `{disp_phys, char_col}` 取出 ASCII 码，再用 `{chr, v_line}` 查字模 ROM 得到该字符当前行的 12bit 点阵，最后用 `pix_col` 从点阵中选出当前像素。字模文件 `vga_font.txt` 按 256 个字符、每个字符 16 行排列，每行一个 12bit 数，bit0 对应最左侧像素。

光标由硬件绘制。软件把当前光标位置写成 `{物理行, 列}` 送入 `0x0021_0004`，显示模块在对应字符格的最下面一行画一条 7 像素宽的横线，并按约 1.5Hz 闪烁。

寄存器里的行号是环形缓冲的物理行，而扫描时得到的是屏幕行，两者相差一个 `top_row`：

$$\mathrm{disp\_row} = (\mathrm{cur\_row} - \mathrm{top\_row}) \bmod 32.$$

硬件先做这个减法，再和扫描行比较，并且只在 `disp_row < 30` 时画光标。省掉这一步减法，光标在第一次滚屏后就会整体下移 `top_row` 行，滚屏次数多了直接移出屏幕。进位用 6 位减法判断：差值的最高位为 1 说明物理行在显示窗口上方，该字符已经被滚出屏幕。

### 2.5 键盘

键盘沿用实验十一的 `ps2_keyboard` 模块。PS/2 时钟经三级寄存器同步，检测下降沿后在数据线上采样。一帧包含起始位、8 位数据、奇校验位和停止位，校验通过后写入 8 项扫描码 FIFO。

`ps2_ascii` 模块取出扫描码并转换成 ASCII 码。需要处理三种情况：

- 断码前缀 `F0`：表示按键释放，后面的扫描码不再产生字符，只用来清除 Shift 状态；
- 扩展前缀 `E0`：方向键、右 Shift 和小键盘回车使用扩展码，单独解析；
- Shift 状态：左右 Shift 分别置位，收到断码时清零，字母和数字键据此输出大写或上档符号。

转换结果写入 16 项 ASCII FIFO。可打印字符原样送入，控制键和功能键映射成不会与可打印字符冲突的控制字节：

| 按键 | 扫描码 | 送入 FIFO 的字节 |
| :--- | :--- | :--- |
| 可打印字符 | — | 对应 ASCII |
| Enter | `5A` | `0x0A` |
| Backspace | `66` | `0x08` |
| Tab | `0D` | `0x09` |
| Home | `E0 6C` | `0x01` |
| End | `E0 69` | `0x05` |
| Up | `E0 75` | `0x11` |
| Down | `E0 72` | `0x12` |
| Right | `E0 74` | `0x13` |
| Left | `E0 6B` | `0x14` |
| Delete | `E0 71` | `0x7F` |
| Ctrl + 字母 | `14` + 字母 | `0x80` 加字母序号，如 Ctrl+L 是 `0x8C` |

Tab 必须按扫描码 `0D` 单独判断，不能走 ASCII 转换表，因为 Enter 的 ASCII 码同样是 `0D`，两者会混在一起。方向键、Home、End、Delete 都在 `E0` 扩展码分支里解析，释放码 `E0 F0 xx` 不产生任何字节。左右 Ctrl 与 Shift 一样单独记录按下和释放状态，按住 Ctrl 时字母键改送 `0x80` 加字母序号，这样 Ctrl 组合键占用 `0x81` 到 `0x9A`，不会和 Home、End 的 `0x01`、`0x05` 冲突。CPU 通过三个寄存器访问这个 FIFO，读数据和出队的分离见 2.3 节。

### 2.6 定时器与板级指示

定时器在 100MHz 时钟域计数到 100000 产生 1ms 使能，32 位毫秒计数从 0 累加，CPU 读 `0x0040_0000` 取得当前值，`time` 命令用它换算成上电以来的秒数。

板上指示灯和数码管用于调试。`LED[15]` 接毫秒计数的一位，约 1Hz 闪烁，用来判断时钟和定时器是否在工作；`LED[14:0]` 由软件写 `0x0060_0000` 控制。八位数码管动态扫描显示 `0x0060_0004` 的调试值，程序把最近一次按键的 ASCII 码写到这个寄存器，显示器没接或者黑屏时也能凭数码管判断键盘是否工作。`SW[15]` 置 1 时数码管改为显示毫秒计数。

### 2.7 软件与编译流程

软件用 C 编写，不链接 C 库，自己实现字符输出、十进制输出和字符串比较。编译链接流程为：

```text
main.c sys.c mul.c
      │  riscv64-linux-gnu-gcc -march=rv32i -mabi=ilp32
      ▼
    *.o ──链接 sections.ld──▶ main.elf
      │                          │
      │                    objdump → main.dump       反汇编检查
      │                    objcopy -O verilog → main.tmp
      ▼                          │
  两个 awk 脚本拆分 ─────────────▶ main.hex   指令存储器镜像
                                   main_d.hex 数据存储器镜像
```

链接脚本把 `.text` 放在 `0x0000_0000`，把 `.rodata`、`.data`、`.bss` 放在 `0x0010_0000`，栈顶设为 `0x0011_FFFC`。`entry` 放在代码段最前面，用两条内联汇编设置栈指针，再跳转到 `main`。

几个关键参数：

| 参数 | 作用 |
| :--- | :--- |
| `-march=rv32i -mabi=ilp32` | 交叉 GCC 默认生成 RV64，必须显式指定 32 位 |
| `-Wl,--build-id=none` | 否则 `.note.gnu.build-id` 落在地址 0，把 `entry` 挤到 `0x24` |
| `-fno-stack-protector` | Ubuntu 默认开栈保护，会引入不存在的 `__stack_chk_fail` |
| `-nostdlib -nolibc -nostartfiles` | 没有 C 库，`*`、`/`、`%` 由 `mul.c` 提供 |

`main.hex` 中的 `@` 是字地址。数据段起始 `0x0010_0000` 对 262144 取模为 0，所以 `main_d.hex` 是从 0 开始的一片独立数据镜像，装入数据存储器的 0 号单元。生成后再把 `main_d.hex` 补齐到 32768 个字，保证 BRAM 中没有未初始化单元。

`mul.c` 只提供无符号的 `__mulsi3`、`__udivsi3`、`__umodsi3`，而 C 语言里 `int` 的除法和取余会调用有符号的 `__divsi3`、`__modsi3`。计算器要算负数，因此这两个函数也补在 `mul.c` 里，做法是按符号转成无符号、调用上面的除法，再把符号补回去。

命令分派在 `run_command` 里，按命令名逐个比较字符串。`calc` 是一个递归下降的整数表达式求值器：`expr` 处理加减，`term` 处理乘除取余，`unary` 处理正负号，`primary` 处理数字和括号，数字支持十进制和 `0x` 十六进制。`mem` 把地址当 `volatile` 指针读，因此能直接看到显存、键盘状态这些内存映射寄存器，也可以查看数据存储器里的变量。

### 2.8 命令行编辑

命令行的编辑全部由 C 软件完成。`readline` 维护一个长度 79 的字符缓冲和一个插入位置，提示符 `> ` 占屏幕偏移 0 和 1，缓冲区第 $k$ 个字符占偏移 $2+k$。偏移换算成屏幕位置为

$$\mathrm{row} = \left\lfloor \frac{\mathrm{off}}{70} \right\rfloor,\qquad \mathrm{col} = \mathrm{off} \bmod 70,$$

超过 70 列的部分自动落到下一行，和实验十一的续行模型一致。编辑开始时把提示符所在行的**物理行**记下来，滚屏只改 `top_row`，物理行不变，所以按键触发的自动滚屏不会打乱后续重画。

按键处理分三类：

- 可打印字符在插入位置写入，右侧字符整体右移；Backspace 和 Delete 分别删除插入位置左边和右边的字符。
- 左右方向键移动插入位置，Home、End 跳到行首和行尾，上下方向键在最近 8 条命令历史里翻找，回到第 0 层时恢复编辑到一半的内容。
- Tab 补全命令名。只有一个候选时补全并在后面加一个空格，多个候选时补到公共前缀。例如输入 `fi` 再按 Tab 得到 `fib `，输入 `he` 再按 Tab 只补到 `hel`，因为 `hello` 和 `help` 都匹配。
- Ctrl+A 与 Ctrl+E 等价于 Home 和 End，Ctrl+U 清空当前行。Ctrl+L 清屏后把已经输入的内容重画在第一行，输入不丢；Ctrl+C 放弃当前行，在行尾打印 `^C` 后换行。

重画策略按代价区分。在行尾追加字符和删除行尾字符时只写一格显存，代价是常数；其余情况整行重画，从提示符开始逐格推进物理行号和列号，不在每个字符上做除法。这样按住一个键连续输入时，每次按键的耗时不会随行长增长，25MHz 下连打 75 个字符也不会让键盘 FIFO 溢出。

### 2.9 扫雷小游戏

`mines` 是一个跑在字符终端上的扫雷，棋盘 9×9、10 颗雷，所有显示都借用现成的字符显存和字模，不需要任何新外设。棋盘用 `#` 表示未翻开，`1` 到 `8` 是周围雷数，空格表示周围没有雷，`F` 是旗子，`*` 是踩到的雷。方向键移动选中的格子，硬件光标正好当选中框用，回车或空格翻开，`F` 插旗，`R` 重开，`Q` 退出。

雷区在第一次翻开时才生成，并且排除首翻格和它周围的 8 格，保证第一下不会踩雷。选雷的办法和 `sgt-puzzles` 的 mines 相同：先把可用的格子列成表，每次用随机数取一个下标，取走后和表尾交换，这样既不会重复也不会出现"反复抽到已占用格子"的死循环。随机数用线性同余

$$x_{n+1} = (1103515245\,x_n + 12345) \bmod 2^{32},$$

取中间 15 位做下标。种子可以写在命令后面，`mines 7` 每次都会得到同一张图，`sw/mines_ref.py` 是同一套算法的 Python 参考模型，用来算 testbench 的期望棋盘。

翻开一格时，如果周围雷数为 0，就从这一格开始做 8 邻接的洪泛，把整片空区一次翻开。洪泛用显式栈而不是递归，栈里存格子编号，进栈前就把格子标成已翻开，所以每个格子最多进栈一次，81 项就够用。游戏每画完一帧把帧号写到数码管寄存器 `0x0060_0004`，上板时数码管会跟着跳，testbench 也用它判断一帧是否画完。

### 4.3 功能仿真

按实验规范，每个上板子实验都配一个自检 testbench，只选代表性用例，不做穷举。本实验写了两个：

| testbench | 层次 | 用例 |
| :--- | :--- | :--- |

第三阶段测 Tab 补全新命令和扫雷。先输入 `ec`、`le` 验证补全成 `echo `、`led `，再用 `mi` + Tab 补成 `mines `，以固定种子 7 进入游戏。棋盘按 `mines_ref.py` 算出的期望值逐格比对：开局全 `#`，翻开左上角后洪泛区域里的数字、未翻开的雷格，插旗显示 `F`、再按一次变回 `#`，走到 (4,1) 这个雷格翻开后显示 `*` 并提示 `BOOM!`，`R` 重开后回到全 `#`，`Q` 退出回到命令行。最后一个用例故意把输入行写满两行再按 Ctrl+C，确认 `^C` 打在第 1 行行尾、新提示符落在第 2 行，光标不会跳回行首。

光标位置单独检查两项。一是读回光标寄存器，把物理行减去 `top_row` 换算成屏幕行，与程序当前所在行比较。二是等 VGA 扫描到光标所在的字符格，检查此刻硬件的光标比较结果确实为 1。第二项能抓到"拿物理行直接和扫描行比较"的错误，因为滚屏后物理行是 30，屏幕上没有第 30 行，光标比较永远不成立。

## 6. 思考题

**1. 如果要实现单步执行，如何通过 `cpuhalt` 控制 CPU 只执行一个周期就停止等待？**

用 `cpuhalt` 和 CPU 时钟做组合，得到一个门控时钟：

$$\mathrm{cpu\_clk} = \mathrm{clk} \;\&\; \neg \mathrm{cpuhalt}$$

CPU 停止时时钟被拉低，PC 和段寄存器保持不变。调试器把 `cpuhalt` 置 0 并给一个完整时钟周期，CPU 就前进一个周期；再置 1 又停住。实现时要注意两点：门控时钟最好用 BUFGCE 生成，避免组合毛刺；`cpuhalt` 只能在时钟低电平期间改变，否则会切出窄脉冲，让部分段寄存器更新、部分不更新。

**2. 如果把 CPU 的指令地址送给 UART 调试模块，是否可以实现断点？**

可以。把 PC 送到 UART 调试器，调试器里比较 PC 是否等于断点地址，相等时把 `cpuhalt` 拉高。为了不打断流水线，比较和停机要在一个完整周期内完成，停机后再把 PC 和寄存器内容通过串口发出去。真正的断点还需要能恢复执行，所以停机时要保存好 PC 和段寄存器，恢复时直接放开时钟。

**3. 如何查看指令和数据存储器中给定地址的内容？**

存储器本身是 BRAM，CPU 访问端口被占用，需要另开一个读端口给调试器。串口调试器收到 `i` 或 `d` 命令后解析地址，把地址送到存储器的一个只读端口，等一个时钟周期后读出数据，再按字节转成十六进制字符逐个发送。数据存储器已经有单独的读端口，指令存储器需要额外加一个读端口，或者复用 CPU 空闲时的取指端口。

**4. 如何查看 CPU 中寄存器内容，需要对 CPU 和 UART 调试器做哪些改造？**

寄存器堆内部是 32 个 32 位寄存器，只连了 CPU 自己的读写端口。要给调试器看，最省事的做法是在 CPU 顶层增加一组调试读端口，把寄存器编号和读数据引出来，调试器按编号逐个读出。另外需要一条暂停 CPU 的信号，因为运行中的寄存器值每个周期都在变，必须停机后再读。改造涉及 CPU 的寄存器堆模块和顶层端口，调试器只需要增加对寄存器编号的解析和输出。

**5. 在 Linux 下，是否可以用 Makefile 脚本直接串口加载代码？**

可以。`objcopy` 生成的 `.hex` 是文本格式，Makefile 里用 `stty` 设置波特率后把文件重定向到串口设备即可：

```bash
stty -F /dev/ttyUSB0 115200
cat main.hex > /dev/ttyUSB0
```

前提是硬件端的 `uart_port` 状态机能解析 `@地址` 行和十六进制数据行，并在加载期间暂停 CPU。这样就把“改代码、重新综合、重新下载”的循环缩短成“改代码、重新编译、串口加载”，迭代速度快很多。

## 个人思考

这次实验里，硬件部分反而比软件部分顺利，因为显示和键盘都是实验十一验证过的结构，CPU 是实验十的副本，主要工作是总线译码和外设寄存器。真正花时间的是两个看起来不起眼的小地方。

第一个是生成 `main_d.hex` 时的一个 awk 写法。我原来的补齐脚本写成了 `awk '/^@/{next} {n++} END{...}'`，本意是统计数据行再补零，结果 awk 只执行最后那个 `END` 块，把所有输入行都丢掉了，生成的数据文件是纯零。这个问题不会报错，编译和链接全部正常，只有仿真里字符串打印不出来才会暴露。后来才发现 awk 里只写条件不写动作等于丢弃该行，必须显式 `print`。这类脚本错误没有编译器帮你检查，只能靠仿真结果反推。

第二个是 testbench 的总线时序。我按“上升沿给地址、下降沿写”的直觉写，结果半字写把整字覆盖成了错误的值。原因是地址在上升沿之后才改变，紧随其后的下降沿读到的还是上一个地址的旧字，读改写的“旧字”是错的。把地址改到下降沿之后给出，和 CPU 里 PC 在下降沿更新的时序一致，问题就消失了。这让我意识到，验证一个存储器的读改写结构时，testbench 必须严格复制 CPU 的真实时序，凭感觉写一个“差不多”的时序只会得到假通过。

还有一件事印象比较深：我用 fib 46 做用例时，程序一直输出 `fib: missing n`。查了半天 C 代码和总线，最后发现是我在 testbench 的扫描码表里漏了数字 4 的映射，按键被发成了 0 号扫描码，硬件直接丢弃。一个测试激励的疏漏伪装成了被测设计的 bug，浪费了不少时间。后来写方向键用例时又犯了一次，字母表里漏了 a，屏幕上只出现 `> b`，我一度以为行编辑的插入位置算错了，其实是 a 根本没发出去。以后写激励表会先把它当作设计的一部分来检查。

加扫雷时遇到一个更隐蔽的问题：游戏一进就卡在半张棋盘上，仿真里只看得到标题和前两行。查了很久才发现不是游戏代码的错，而是我在 `main.c` 里新加的两个函数定义在了 `entry` 前面，链接器就把它们排到了 `.text` 的最前面。CPU 复位后从地址 0 取指，根本没进 `entry`，直接跑进了其中一个函数，`ra` 还是 0，于是不停来回跳。以前一直默认"`entry` 在最前面"是天然成立的，其实是靠"`entry` 是文件里第一个函数"这个巧合。修完之后我在 Makefile 里加了检查：`objdump` 出来的第一行不是 `00000000 <entry>:` 就直接报错停下，免得下次再踩。

光标错位是这次花时间最多的一处。现象是滚屏几次以后光标跑到别的行上，滚得越多偏得越远。我先怀疑软件算错了行号，把光标寄存器的值打印出来，物理行是对的；再在 testbench 里同时打印 `top_row` 和光标值，一眼就看出来：滚了 6 行以后寄存器里是物理行 3，屏幕上那一行在显示第 29 行，比较的时候差了整整 26 行。原因很直接，寄存器存的是环形缓冲的物理行，扫描时拿到的是屏幕行，中间少做了一次减 `top_row`。改法是加一个 6 位减法，差值为负说明这一行已经滚出屏幕，不画光标。

这件事之后我给这条用例补了一个反向验证：把比较逻辑临时改回旧写法重跑，testbench 必须报错，确实报了 `cursor_here=0`。以前我判断一个用例"通过"就看它跑完打印 TEST PASSED，现在会先问一句，这个用例在错误的实现上会不会失败。不会失败的用例只是把流程走了一遍，什么也没证明。

最后关于内存映射，我一开始以为 `0x0020_0000` 和 `0x0021_0000` 只差在地址的高位，查过才发现它们的高 12 位完全相同，只有 `addr[19:16]` 不同。如果把显存和寄存器都按高 12 位译码，光标寄存器会被当成显存的一个字节，看上去写进去了，实际屏幕上一个字符都不会变。改成显存按 `addr[31:16]`、寄存器按整字地址比较之后才正常。这件事说明地址划分表不能只写个“大概范围”，每一段的译码位宽都要算清楚。
